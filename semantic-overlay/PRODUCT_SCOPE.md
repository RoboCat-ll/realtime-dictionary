# 实时字典产品范围（验证阶段）

## 唯一要验证的问题

微信或 QQ 桌面聊天中出现陌生技术概念时，实时字典能否比复制、切换应用、搜索更快地帮助用户恢复理解，并且不会造成明显干扰。

## 正式范围

- Windows 微信桌面版与 QQ 桌面版，共用同一套交互和验收标准。
- 单次消息解释：先按 `Ctrl+Alt+K`，再在 10 秒内点击一条 1-1000 字的微信或 QQ 消息；点击后自动退出待选状态，先理解整条消息，再按需查看原文中的术语。
- 完整无障碍消息文字优先；客户端未提供时，本地定位整个消息气泡并 OCR。拖选矩形不能再冒充多行消息全文。
- 一次请求只发送选中的段落，返回整段中文解释和 0-5 个必要术语；术语必须逐字存在于原文，不为凑数量强行输出。
- `Ctrl+Alt+D` 保留为直接查词入口；拖选后的就地按钮只作为单击消息识别失败时的兜底。

## 实验范围

- 全窗口 OCR 自动高亮降为显式的兼容实验入口，不再由默认托盘动作或默认快捷键启动。
- 会议字幕、日程、提醒和浏览器扩展保留代码，只修复崩溃、安全和数据损坏问题。它们不进入首次使用主流程，不作为当前版本成熟度的依据，也不接受新增功能。

## 明确不承诺

- 不承诺任何软件、任何布局都能工作。
- 不承诺 OCR 高亮能达到应用原生文字逐帧跟随效果。
- 不以离线测试数量、模型已连接或窗口已出现作为用户任务完成的证明。
- 不把未点击自动等同于无价值；必须结合明确反馈和持续使用判断。

## 核心路径

### 单次消息解释（基线）

按 `Ctrl+Alt+K` → 进入 10 秒待选状态 → 点击一条消息一次 → 自动退出待选状态 → 完整无障碍文字，或整个消息气泡 OCR → 使用独立的低延迟消息解释模型 → 先显示整句话的通俗含义 → 再显示校正后的原句并把必要术语做成可点击高亮 → 点击后在同一面板追加语境注释。未进入待选状态的普通点击不触发识别或模型请求。OCR 校正必须通过保守相似度校验；只允许技术词、标点、空格以及由同一消息上下文唯一确定的 1-2 个中文漏字修复，必须保留所有可辨认片段，禁止润色或改写；无障碍精确文字不改写；原始 OCR 编辑收在显式纠错入口中。模型遗漏的原句精确本地术语仍保留，拖选与手工修改只作为失败兜底。

### 主动查词（辅助）

选中文字后按 `Ctrl+Alt+D` → 精确文字或可编辑局部 OCR → 中文词义解释。

### 自动高亮（兼容实验）

稳定聊天画面 → 本地候选与坐标 → 本地强候选立即显示 → Jev 后台判断模糊候选 → 只追加、不闪空 → 点击后复用同一解释卡片。

## 决策门槛

- 微信与 QQ 合计至少 50 次真实消息点击，95% 的完整无障碍消息无需人工修正；气泡 OCR 单独统计修正率。
- 5 名目标用户中至少 3 人在第二周无需催促仍主动使用。
- 自动高亮必须相对主动查词缩短理解恢复时间、获得明确偏好或发现用户原本不会查询的重要概念；否则默认关闭。
- 若一个明确聊天场景都没有持续使用，停止扩场景并重新验证需求。
