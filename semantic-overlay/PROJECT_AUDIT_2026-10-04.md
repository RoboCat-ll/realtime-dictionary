## 确定问题：固定修复清单

### A01 · P1 · 损坏提醒文件被空数据覆盖（复现）

- 证据：`native-host/LocalReminders.cs:159`，反序列化失败后变为空列表，随后只要文件存在就保存。
- 实验：向临时文件写入 `{broken`，构造 Store 后原文件内容变为 `[]`。
- 影响：读失败变成不可逆覆盖，原文件中可能可恢复的提醒内容丢失。
- 修法：区分“加载成功”和“加载失败”；失败时不覆盖原文件，显示读取错误并提供明确恢复入口。后续保存也须防止默默覆盖未恢复的损坏文件。需要备份/迁移真实数据时另行获得授权。
- 验收：破损 JSON、锁定文件和无权限三类输入均保持原字节；恢复失败时不冒充空历史；正常创建、删除和重启仍成功。
- 状态：已修，隔离文件保留/禁止覆盖回归通过；未改真实数据。

### A02 · P1 · 提醒删除/稍后提醒保存失败，内存与磁盘不一致（复现＋源码）

- 证据：`LocalReminders.cs:139`、`:148` 先修改内存再 Save；提醒弹窗的回调 `:271`、`:277` 吞掉保存异常。
- 实验：创建合成提醒，锁定文件后调用 Dismiss：保存报 IOException、内存条数为 0；解锁重建 Store 后条数为 1。
- 影响：用户以为删除成功，重启却再次出现；稍后提醒也可能重启后恢复旧时间。
- 修法：在副本上操作，持久化成功后发布内存状态；回调根据结果关闭窗口或提示失败，不能无条件消失。创建操作已有失败回滚，可沿用同一语义。
- 验收：创建、删除、稍后提醒分别注入写失败；界面、当前内存、重新加载后的数据保持一致，失败可重试。
- 状态：已修，失败提交不改变内存，提醒弹窗保留；隔离回归通过。

### A03 · P1 · 非尺寸偏好保存失败仍能逸出 UI 事件（源码）

- 证据：`ServiceManager.cs:273`、`:280`、`:287`、`:293`、`:300` 等设置函数先改内存，再直接调用 SetAndSave；`TrayMenu.cs:42` 的连续开关点击没有处理该异常。PreferenceStore 的写入异常会向上传播。
- 影响：只修复“拖尺寸时保存失败”还不够；同一目录写失败时，菜单切换仍可能弹未处理异常，运行开关和磁盘值也会不一致。
- 修法：统一设置结果接口，区分已保存、仅本次生效、失败；由 UI 给出简短提示并刷新真实状态。不要仅加全局异常吞掉后继续冒充成功。
- 验收：在隔离只读/被锁配置上，连续查词、字幕保存、触发方式和实验功能开关均不逸出异常；重启恢复值与提示一致。
- 状态：已修，保存失败仅本次生效并通知，损坏偏好尺寸保存异常已覆盖。

### A04 · P1 · 主流程未受“本小时分析上限”控制，展示口径不一致（复现）

- 证据：`server.py:1820` 的 reserve_model_analysis 只由兼容 `/analyze` 路径调用；`:2465` 的 analyze_selection 不调用它。`OverlayContext.Configuration.cs:148` 将这组计数展示为模型/本小时分析状态。
- 实验：将隔离额度设为 1 且已满，调用 analyze_selection，模型 mock 仍被调用，结果为 model。
- 影响：主要消息解释不能用该计数判断请求量或额度保障；它也不代表物理重试次数和所有模型接口。
- 修法：先明确额度定义。最小修正是把现有状态明确标成“兼容扫描分析”，主流程展示独立用量；若保留产品级预算承诺，再对消息、查词、翻译统一预约额度。缓存命中、物理重试和语音独立计量，不把三种计数混成一个数字。
- 验收：额度已满时目标受控接口不发送请求；并发不能越界；缓存不误扣；认证失败与未知用量如实报告；托盘数字与对应测试账目相符。
- 状态：已修展示口径：小时上限仅兼容整窗扫描，未新增全局预算。

### A05 · P2 · 单字符消息被无障碍路径直接排除（复现）

- 证据：`MessageTextReader.cs:176` 排除 `text.Length < 2`，而产品输入约定为 1–1000 字符；OCR 气泡检测还有最小宽度/面积限制。
- 实验：合格 Text 控件边界内的“好”，IsCandidate 返回 False。
- 影响：即便客户端提供完整文本，“好”“嗯”等一字消息也不能走精确取句路径；不保证 OCR 兜底一定补上。
- 修法：允许长度为 1 的文本，保留控件种类、位置、时间标签等排除条件；用这些条件排除头像、按钮和姓名，不能靠长度一刀切。
- 验收：单字符消息可读取，图标/按钮/姓名与非消息单字符不被误送；QQ/微信各补真实案例。
- 状态：已修，单字符文本与按钮负例诊断通过；真实客户端另验。

### A06 · P2 · 两个接口字段类型缺少验证，错误输入直接断连（复现）

- 证据：`server.py:2750`、`:2793` 对 text/term 直接 `.strip()`，没有 `/selection/analyze` 已有的字符串校验；这两个入口也缺少明确字段长度上限。
- 实验：隔离回环 POST `text:123` 或 `term:123`，客户端收到 RemoteDisconnected，服务线程发生 AttributeError。
- 影响：兼容或内部调用异常不能得到稳定错误；合法 JSON 并不等于合法字段。这里只影响对应请求线程，未证明整个服务崩溃。
- 修法：复用统一字段验证，拒绝非字符串，给兼容扫描与查词分别定义合理上限；稳定返回 400，不静默裁剪。
- 验收：数字、数组、对象、超长字符串返回明确 400，且未调用 OCR/模型；正常请求不回归。
- 状态：已修，类型/长度错误返回 400，隔离接口回归通过。

### A07 · P2 · 字幕全会话按末条文本去重，会漏掉真实重复发言（源码）

- 证据：`OverlayContext.Audio.cs:252` 只比较规范化后的文本与 lastAudioTranscriptIdentity；无音频块身份、时间距离判断，值仅在新会话时重置。
- 影响：上一条是“Yes”，之后即使隔了一段静音再次说“Yes”，也会被当重复丢弃。大小写和标点变化也被归一掉。
- 修法：只消除可证明由重叠片段/重试造成的重复；利用块 ID、采集时间和重叠窗口，保留间隔后的真实重复。
- 验收：同块重试不重复；不同块的间隔重复被保留；重叠首尾不重复；原始文本归档一致。
- 状态：已修去重身份，合成不同采集块重复与同块重试通过；实音频待验。

### A08 · P2 · 字幕历史超限或不可读时被静默跳过（源码）

- 证据：`CaptionForms.cs:171` 整个文件超过 20 MB 就跳过；`:210` 吞掉单文件读取错误；`:212` 超过 20000 条删除最早显示数据。LoadDate 只返回列表，没有遗漏状态。
- 影响：记录窗口可能显示“这一天暂无已保存字幕”或普通条数，无法区分真为空、未读成功和已截断。不是所有记录都从磁盘删除，而是用户回看不到。
- 修法：保留内存/文件安全限制，增加读取结果状态和遗漏数量；采用分段/分页读取大历史，不能为了显示全部一次性取消上限。
- 验收：超限、损坏、锁定和部分可读的合成档案均给出明确状态；可读部分仍可查询/导出，不冒充完整历史。
- 状态：日期窗口已修为有界分页与明确遗漏提示；超大/损坏档案与前后页通过。旧兼容读取接口保留上限。

### A09 · P2 · 打开历史窗口时，每条字幕同步重读整天文件（源码）

- 证据：`OverlayContext.Audio.cs:275`、`:306` 刷新历史；`CaptionForms.cs:980` 在窗口可见时直接调用 ArchiveDateRequested，实际绑定 LoadDate；它逐文件读取、排序，再构造整段显示文本。
- 影响：持续录制时工作量随当天历史增长；即便回看旧日期也会重复读旧文件。磁盘读取发生在 UI 调用链上，存在可避免的卡顿来源。本轮未测得具体卡顿秒数。
- 修法：录制日期一致时增量追加；旧日期不随新字幕刷新；完整读盘改为后台并检查日期世代，追加合并节流。保持现有选区和滚动位置约定。
- 验收：预置大档案后，追加一条不全量读盘；旧日期读次数不增长；切日期迟到结果不覆盖；滚动/选词不丢失。
- 状态：已修增量追加、后台读页、界面线程回写与旧日期世代隔离；并发/选区诊断通过。

### A10 · P2 · 偏好保存失败遗留临时文件（复现）

- 证据：`PreferenceStore.cs:41` 创建随机 tmp，Replace/Move 失败无 finally 清理；提醒存储已经有相应 finally。
- 实验：锁住合成 prefs 文件后保存，失败后遗留 1 个 `prefs.json.*.tmp`。
- 修法：清理仅本次操作创建的临时文件，清理失败不得覆盖原始错误。不要扫删用户目录里的所有 tmp。
- 验收：连续注入写/替换失败不积累文件；旧设置字节不变；成功的并发保存保持锁保护。
- 状态：已修，失败路径只清理本次临时文件，隔离回归通过。

### A11 · P2 · 宿主和后端运行日志没有大小/轮换限制（源码）

- 证据：`ServiceManager.cs:791` 和 `server.py:2835` 持续 append；`start.ps1` 会读取宿主日志检查启动事件。浏览器轮询已退休，旧版“每个标签页不断产生日志”的原因不再存在。
- 影响：长期使用仍累积磁盘和日志读取成本；故障排查缺少跨日保留策略。
- 修法：有限大小轮换，保留有限份数；日志保持类别、耗时、错误类型，不加入聊天原文或密钥。启动验证只读取本次必要尾部。
- 验收：合成高频日志达到阈值后，总量有界；并发/文件占用不影响解释；本次启动事件仍能识别。
- 状态：已修有限轮换及启动脚本增量读取，轮换回归/脚本语法通过；真实启动待验。

### A12 · P2 · 现有指标不能证明用户端故障率与完整响应时间（源码）

- 证据：`MessageExplanationForms.cs:432` 在取句完成、面板开始分析后才启动计时；`:488` 记录分析结果。`OverlayContext.Input.cs:218` 的取句失败/忙碌/取消主要写运行日志，未进入同一操作统计。`UsageMetrics.cs:129` 超过 5 MB 后静默停止追加。
- 影响：只统计打开面板后的成功/失败，不能代表“用户触发→读句→最终可见结果”的分母或耗时；缓存与重试还需分层。长期采集也可能停止，而界面无提示。
- 修法：每次明确触发分配匿名操作 ID，记录读取、最终结果、明确失败/取消等终态和全程耗时；不记消息内容。统计滚动文件并标记采集失效，缓存、未缓存、输入来源、物理请求分开。
- 验收：合成 10 次含取句失败、取消、缓存和超时，事件终态数量/分母准确且无重复；全程时间包含 OCR；达到文件上限仍可按策略记录；不泄漏内容。
- 状态：已修消息点击匿名终态与完整链路计时、指标轮换/失败提示；十操作合成验证通过。仍不能据此宣称真实故障率低于 1%。

### A13 · P1 · 微信 AIGC 误读成 ACC（历史实测，未本轮重现）
